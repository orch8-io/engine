## 2025-11-05 - [Replace HashMap Allocation with Flat Vec for Block Lookup]
**Learning:** In the `flatten_blocks` function within `orch8-engine/src/evaluator.rs`, allocating a `HashMap<&BlockId, &BlockDefinition>` to map execution blocks introduces significant hashing and memory allocation overhead on the evaluation hot path, which is called every tick. Since the tree size is typically bounded and small, building a `Vec` and sorting it by `BlockId` allows for O(log N) lookups via `.binary_search_by_key()`, completely avoiding `HashMap` overhead.
**Action:** In execution hot paths where a lookup map is created from a slice on every iteration, always prefer a flat `Vec` initialized with `Vec::with_capacity()`, sorted by key, and queried via `.binary_search_by_key()` over a `HashMap` to eliminate hashing and heap allocation costs.

## 2025-11-05 - [Replace Intermediate Collection Allocation with Direct Map Query]
**Learning:** In the `emit_sla_alerts` function within `orch8-engine/src/scheduler.rs`, the original code allocated a `HashSet` from a map's keys just to perform existence checks against the map. Later, an attempt was made to optimize this by building a sorted `Vec` and using `binary_search`. Both approaches are wrong. Building *any* intermediate collection (Set or Vec) to check for existence when the underlying data is already stored in an $O(1)$ lookup structure (like a `HashMap`) is a severe anti-pattern.
**Action:** In execution hot paths, when checking for existence against a pre-fetched `HashMap` or `BTreeMap` result, directly query the map using `.contains_key()` instead of allocating and populating intermediate structures like `HashSet` or `Vec`.
