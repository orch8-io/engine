# Orch8 Rust crate review

Reviewed the working tree at `4a54942a`, including 185 tracked modifications and untracked paths reported by Git at the start. The review covers all 13 workspace crates, the standalone Node, Python, and fuzz crates, and the vendored SQLite driver patch. It samples public entry points, persistence and authorization boundaries, failure and recovery paths, release jobs, and representative tests. The TypeScript dashboard was inspected where it consumes Rust placement and effect-review reports. A standalone frontend and BigQuery audit were outside the Rust crate scope.

The review found four high-priority and twelve medium-priority issues. The council lenses were code quality, Rust API and ownership, system architecture, workflow consistency, release engineering, and engineering laws, followed by technical opportunity and documentation review. The previous workspace report was used as a baseline. The working tree now has rotating gRPC demand, gRPC pin lookup, a bounded background-task drain, pinned-child contracts, structured fuzz targets, documented native scheduling budgets, and a linked SQLite host probe. The findings below cover their remaining gaps and other paths.

## Highest-leverage change

**Put claim eligibility in the same transaction as the claim, then use the same decision rules to explain placement.** HTTP and gRPC accept the same version policy today, but both resolve it before asking storage to mutate a task. The placement preview also uses a separate worker inventory. Add the validated worker version to the existing claim request. Have SQLite and PostgreSQL serialize pin updates with admission for the applicable tenant and handler, including first-time pins. Make readiness consume transport-aware worker observations and shared admission rules.

Start with a matrix covering HTTP, unary gRPC, and streaming gRPC on each backend. Include an unpinned route, a staged pin, promotion between poll and claim, rollback, omitted versions, named queues, and the documented behavior for unscoped workers. Keep the existing issued-claim journal, epoch fences, and placement checks in the write path. This work addresses H1 and H2, enables M1 and M2, and gives the E2E harness a reusable contract. Estimated effort is 1–3 days for the first end-to-end slice.

## High priority

| ID | Finding and impact | Change and acceptance check | Effort |
|---|---|---|---|
| **H1** | **Worker version checks have a race across promotion.** HTTP and gRPC read the active minimum before constructing the claim request, which carries neither a version nor the observed policy revision. A poll can read the old pin, a promotion can commit, and that poll can still commit an incompatible claim. This affects rollout consistency within tenant-scoped paths. [HTTP claim](../../orch8-api/src/workers.rs#L826) · [gRPC demand](../../orch8-grpc/src/service.rs#L702) · [Claim request](../../orch8-storage/src/worker_claim.rs#L170) · [PostgreSQL claim write](../../orch8-storage/src/postgres/worker_claim_candidates.rs#L67) | Evaluate and fence the pin at the authoritative write. Hold a claim at a test barrier, promote the pin, then resume the claim. Assert the old-version task stays pending, with a passing case for a compatible worker on each backend. | L |
| **H2** | **Fleet readiness misses gRPC-only workers.** Readiness iterates worker registrations, while gRPC streams persist runtime capabilities and use a version from request metadata. A worker with only a live gRPC stream can claim work while the preview says to start a worker, causing `placement fleet-readiness` to exit unsuccessfully. [Inventory fetch](../../orch8-api/src/placement/plan.rs#L116) · [Eligibility loop](../../orch8-api/src/placement/plan.rs#L333) · [gRPC registration](../../orch8-grpc/src/service.rs#L408) · [CLI gate](../../orch8-cli/src/commands/placement.rs#L63) | Record tenant, transport, handler, queue, version, and freshness through one inventory interface. Treat capacity as unknown when it is unavailable. Verify that an HTTP-only and a gRPC-only worker each appear on the exact routes their transports support. | M |
| **H3** | **Package install can leave a partial deployment that retries cannot resume.** The CLI alternates conflict checks and sequence creation, and records package provenance only after all uploads and follow-up requests succeed. If a later sequence fails or a response is lost, the retry encounters the earlier sequence and aborts as a conflict. [Install loop](../../orch8-cli/src/commands/package_cmd.rs#L639) · [Provenance write](../../orch8-cli/src/commands/package_cmd.rs#L733) | Validate the entire package before any write. Make publishing transactional, or persist a resumable install keyed by content hash and verify exact existing definitions on retry. Test failure after the first create and a lost success response. Preserve rejection of unrelated conflicting definitions. | L |
| **H4** | **The server’s 30-second drain starts after HTTP has finished.** The HTTP server is awaited before the bounded join of engine, gRPC, outbox, and breaker tasks. SSE producers already observe shutdown, but a stalled ordinary request or response can hold HTTP graceful shutdown before this timer starts. Telemetry shutdown follows the timed join. [HTTP await and background drain](../../orch8-server/src/main.rs#L536) · [Timed helper](../../orch8-server/src/main.rs#L1567) · [SSE cancellation](../../orch8-api/src/streaming.rs#L316) | Start one process drain deadline when shutdown is signalled. Bound HTTP drain and any awaited telemetry work within it. Add a process-level test with one stalled HTTP request and one healthy request that finishes before the deadline. | M |

## Medium priority

| ID | Finding and impact | Change and acceptance check | Effort |
|---|---|---|---|
| **M1** | **Placement preview loads the global worker fleet.** The API fetches all recent registrations, both backends sort and fetch them in full, and the API filters by tenant afterward. Eligible worker IDs can then repeat on every matching sequence step. The existing inventory cap applies to runtime capabilities. [API fetch and filter](../../orch8-api/src/placement/plan.rs#L123) · [Response fields](../../orch8-api/src/placement/plan.rs#L43) · [PostgreSQL query](../../orch8-storage/src/postgres/workers.rs#L1337) · [SQLite query](../../orch8-storage/src/sqlite/workers.rs#L1238) | Query by tenant, freshness, and the sequence’s route keys. Return counts plus bounded samples, with typed completeness information. Benchmark rows read and response bytes as unrelated tenant registrations grow. | M |
| **M2** | **Worker version ordering changes with the operand pair.** Numeric values compare component-wise. Any nonnumeric operand triggers lexical ordering. This admits inconsistent ordering across mixed formats, for example `2 < 10 < 1z < 2` under pairwise comparison. The publisher independently requires numeric app and SDK versions. [Worker comparator](../../orch8-types/src/worker.rs#L700) · [Catalog comparator](../../orch8-publisher/src/catalog_rollout.rs#L240) | Model numeric versions and named build identifiers as explicit schemes. Define inter-scheme compatibility and test existing numeric and date-stamped pins during migration. Use the same typed eligibility in preview and claims. | M |
| **M3** | **Pinned child contracts share a mock namespace across definitions.** The runner applies block mocks and recorded outputs by bare block ID across the root and all children. Separately authored definitions can use the same ID. Assertions read the root instance’s outputs, so a direct child assertion has no equivalent scoped selector. [Mock lookup](../../orch8/src/contract.rs#L179) · [Recorded mock](../../orch8/src/contract.rs#L221) · [Output assertions](../../orch8/src/contract.rs#L365) | Add definition-qualified mock and output selectors while preserving root-only suites. Reject ambiguous selectors during validation. Test a root and child that both use `validate` with different expected results. | M |
| **M4** | **Package contract checks omit pinned dependencies.** Package install passes default run options, which leave the child catalog empty. The same graph can be tested with explicit child definitions via `orch8 test run`, then be rejected during installation. The installer also warns and skips a contract whose root document is missing. [Package contract gate](../../orch8-cli/src/commands/package_cmd.rs#L605) · [Contract run options](../../orch8/src/contract.rs#L39) · [CLI child input](../../orch8-cli/src/commands/test_cmd.rs#L108) | Load and validate the archive’s definition graph once. Supply reachable pinned children to each packaged suite and fail on orphaned contracts. Test an archive with a passing pinned child and one with the child missing. | M |
| **M5** | **Sub-sequence completion materializes every child output.** The engine reads all child outputs and serializes whole output records into the parent block. In deep chains, the same descendant output travels through and is persisted at successive ancestors. [Child completion](../../orch8-engine/src/evaluator/dispatch.rs#L325) | Measure bytes read, serialized, and stored for a nested chain with representative outputs. Define a child-result contract with bounded materialization, keeping the existing representation available to workflows that rely on it. | M |
| **M6** | **Replay export caps the finished fixture after retaining selected outputs.** Each chosen value can occupy up to 512 KiB in the intermediate map. The aggregate check runs after storage paging, cloning, and redaction. Requests that will fail the final limit can still allocate and process substantially more than 512 KiB. [Selection limits](../../orch8-api/src/releases/replay_fixture.rs#L27) · [Accumulation and late check](../../orch8-api/src/releases/replay_fixture.rs#L151) | Select latest outputs in storage and account for bytes as values are retained. Keep explicit row and input limits. Test a superseded large output and a selection whose latest values exceed the budget in aggregate. | M |
| **M7** | **The effect review queue has no continuation cursor.** The endpoint fetches 101 rows and emits the oldest 100 with `has_more`. If old effects remain unresolved, operators cannot reach later records through the queue. The database already indexes the sort keys. [Review endpoint](../../orch8-api/src/continuity/effect_review.rs#L25) · [Review index](../../migrations/145_effect_review_queue.sql#L1) | Add keyset pagination on `(updated_at, id)` and carry the cursor into the dashboard. Verify stable paging for equal timestamps and document how refreshed rows re-enter the queue. | S |
| **M8** | **The bundled mobile install result conflates several expected outcomes.** The legacy catalog returns zero when all names already exist or when a synced manifest has taken ownership. An app cannot tell whether repeating setup is appropriate from the result. Seeding is already atomic and limited to missing names. [Mobile seed transaction](../../orch8-mobile/src/storage/manifest.rs#L122) · [SDK behavior](../MOBILE_SDK.md#signed-first-launch-catalogs) | Expose a typed disposition with installed and skipped counts through a compatible SDK entry point. Add a packaged-host case that installs a seed, accepts a manifest, restarts, and confirms the seed cannot restore withdrawn definitions. | M |
| **M9** | **An issuance retry generates a new catalog delivery.** Each call signs a new manifest and replaces `last_issued`. A lost response or overlapping retry can supersede a receipt that the device is about to acknowledge. The caller already owns cursor persistence. [Issue and acknowledge](../../orch8-publisher/src/catalog_rollout.rs#L120) · [Host persistence contract](../../orch8-publisher/CATALOG_ROLLOUT.md#serve-and-acknowledge) | Put an issuance idempotency key and durable delivery lookup in the host integration. Test that two retries return the same receipt and that genuinely newer policy generations supersede it. | M |
| **M10** | **Push retry counts describe outbox leases rather than provider requests.** APNs has up to three delivery attempts inside a lease, and the durable outbox schedules another lease for retryable failures. The provider deadline bounds time, while the lease attempt count obscures actual send volume. [APNs budget](../../orch8-push/src/apns.rs#L15) · [Outbox result handling](../../orch8-push/src/outbox.rs#L287) · [Provider deadline](../../orch8-push/src/outbox.rs#L362) | Record HTTP attempts per lease and define one observable retry budget. Compare retry and rate-limit behavior before merging the loops. Test temporary failure, token refresh, and terminal token rejection. | M |
| **M11** | **WASM preview bounds operations and step attempts, with no trace-byte budget.** Each successful attempt copies the output into its timeline entry. A single 16 KiB mock repeated 512 times produced an 8.59 MB serialized result in the host probe. [Interpreter result](../../orch8-wasm/src/interp.rs#L186) · [Output copy](../../orch8-wasm/src/interp.rs#L697) | Cap detailed trace bytes independently from ticks and expose truncation to the caller. Preserve final state and a compact execution timeline. Assert the response ceiling with repeated large mocks and measure memory in the browser. | M |
| **M12** | **Release Rust builds do not enforce the tested lockfile.** The tag gate checks CI for the exact commit, and CI uses locked builds. The release commands for server, CLI, iOS, Android, and binding generation invoke Cargo without `--locked`. This permits lockfile resolution changes in the jobs that produce shipped artifacts. [Tag gate](../../.github/workflows/release.yml#L55) · [Server and CLI release](../../.github/workflows/release.yml#L157) · [Mobile release](../../.github/workflows/release.yml#L399) · [Binding generation](../../.github/workflows/release.yml#L487) | Require locked Cargo resolution in each release producer and record the lockfile checksum alongside target and artifact digest. Verify each artifact job fails with an intentionally stale lockfile on a test branch. | S |

## Verification and performance

- The locked offline host workspace check and the browser WASM target check passed. All standalone lockfiles resolved for the host. Formatting and whitespace checks passed.
- The four selected library suites passed 1,191 unit tests after rerunning loopback-dependent fixtures with permission to bind locally. The publisher passed 122, push 101, types 749, and WASM 219. An additional 24 embedded contract tests passed, including pinned-child success, failure, and cancellation.
- Instrumented `orch8-types` library tests reported 91.28% line coverage and 89.11% function coverage. Sequence validation reached 88.05% line coverage and delegation wire code 93.78%. The figures cover that crate’s unit-test build.
- The cached advisory database at commit `40f5be6f` dated 2026-10-28 reported zero matching vulnerabilities across the four lockfiles and one root maintenance advisory, `RUSTSEC-2026-0374`. The linked probe against the existing host debug mobile archive reported SQLite 3.54.1.
- The performance probe used a freshly built host dev library and ten runs per size. The input contained one 16 KiB mocked output reused within a `for_each` body. Timings include options and sequence decode, execution, and JSON response serialization.

## Fix order

1. **Next release** — fix H1 and H2 together, then run the transport/backend acceptance matrix. A coding agent can implement the crate changes. The operator should confirm the existing unscoped-worker policy before expanding enforcement.
2. **Next release** — fix H4 and add a stalled-HTTP process test. Add locked resolution to release jobs independently. A coding agent can prepare both changes.
3. **Package deployment** — address H3 and M4 as one install flow. The operator should choose transactional publication or durable resumability based on the existing API contract. A coding agent can implement the acceptance cases and the selected protocol.
4. **Next iteration** — prioritize M11, M6, and M7 as bounded changes. Add production evidence before changing result formats, scheduler queries, provider retry behavior, or storage trait boundaries.

Re-review when the claim matrix is green on both databases and all three transports. Before the next server release, run the process drain test with a stalled HTTP request and the package retry test with a lost response.
