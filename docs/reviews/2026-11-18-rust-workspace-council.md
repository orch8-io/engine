# Orch8 Rust crate technical review

## Scope and method

Reviewed all 17 Rust crates at `4a54942a`, including local changes present during inspection. The repository has 18 Cargo manifests. The virtual root declares 13 workspace members, and the remaining four manifests describe the Node binding, Python binding, fuzz harness, and vendored SQLite driver. The review sampled each crate's entry points, state and error handling, and tests, then followed the contracts across HTTP, gRPC, native, and playground execution. The vendored driver review focused on Orch8's patch, dependency resolution, and release verification.

Metadata puts `orch8-types` on 11 crates' direct production dependency lists, `orch8-storage` on eight, and `orch8-engine` on seven. These are the highest-leverage places to narrow contracts. The review found useful existing boundaries in typed storage transitions, generation-bound worker claims, package verification, and backend-parity tests. Build on those contracts when extracting responsibilities.

## Prioritized findings

| Priority | Finding and evidence | Action and acceptance test | Effort |
|---|---|---|---|
| High | **gRPC demand can starve later handlers.** Each demand starts at the beginning of `open.handler_names` and stops as soon as the requested capacity is full. A continuously busy first handler can leave the next handler untouched across successive demand frames. [Stream demand](../../orch8-grpc/src/service.rs#L644) | Rotate the starting handler per session and preserve the existing outstanding-work cap. Use a capacity-one stream with sustained backlog in the first handler and assert bounded service for the second. | S |
| High | **Rollout policy has a transport boundary.** Tenant-scoped HTTP checks version pins before claiming. gRPC stream demand and unary claims use their own admission path. This scope is documented. A mixed fleet needs a release-readiness decision that accounts for both transports. [HTTP admission](../../orch8-api/src/workers.rs#L634) · [gRPC claims](../../orch8-grpc/src/service.rs#L2044) · [Placement guide](../PLACEMENT.md#stage-and-roll-back-worker-version-pins) | Put placement, version eligibility, and claim authority behind one admission contract. Add a gRPC worker version capability with explicit behavior for existing clients, then run the same promotion and rollback cases against both transports and databases. | M |
| High | **Circuit-breaker persistence can extend shutdown beyond the drain deadline.** The server times its task join for 30 seconds and awaits a separate unbounded tracker flush afterward. The tracked writes await storage. A stalled write can keep shutdown open until its lower-level operation finishes. [Server drain](../../orch8-server/src/main.rs#L1557) · [Tracker flush](../../orch8-engine/src/circuit_breaker.rs#L237) | Apply one overall shutdown deadline with a persistence allowance. Test shutdown with a deliberately held persistence future and verify the deadline, clean-path durability, and timeout diagnostics. | S |
| Medium | **The playground and contract runner answer different questions for child workflows.** WASM emits a mocked child and can report `completed`. The native contract runner rejects a child sequence because the sandbox registers only the root. [Playground child dispatch](../../orch8-wasm/src/interp.rs#L374) · [Native contract runner](../../orch8/src/contract.rs#L113) | Expose the verification scope in results and add a cross-runner fixture suite. Prioritize exact pinned children and failure/cancellation paths. Share the definition walk before considering a shared interpreter. | M |
| Medium | **The storage aggregate makes narrow consumers depend on a broad surface.** The aggregate includes instance state, workers, scheduling, telemetry, AI, tenancy, continuity, and push. Both engine and API state accept the aggregate. Existing subtraits offer a migration path. [Storage aggregate](../../orch8-storage/src/lib.rs#L5648) · [API state](../../orch8-api/src/lib.rs#L117) | Start with narrow read-side dependencies and retain aggregate adapters at composition roots. Add parity contracts for authorization and atomic writes before moving backend logic. | M |
| Medium | **Cold scheduler sweeps can serialize lookups for many sequence revisions.** The waiting sweep pages instances and awaits sequence cache resolution per instance before batching output reads. Cache hits and the SLA memo reduce the steady-state cost. [Waiting sweep](../../orch8-engine/src/scheduler.rs#L1815) · [SLA sweep](../../orch8-engine/src/scheduler.rs#L2525) | Measure one cold page with distinct sequences on PostgreSQL. Batch cache misses if query count and latency justify it. Keep the existing batched output and signal reads. | S |
| Medium | **Node and Python `run` timeouts leave storage reads unbounded by the caller's deadline.** Both wrappers describe running until settlement or timeout. The shared implementation limits scheduler work and waiting, while engine initialization, instance reads, and the final snapshot await storage separately. A slow read can extend the call past the requested duration. [Node contract](../../packages/node-native/index.js#L86) · [Python contract](../../packages/python-native/python/orch8_engine/__init__.py#L144) · [Shared run loop](../../packages/native-common/durable.rs#L294) | Define explicitly whether the timeout covers the call or scheduler work. For a call-wide deadline, bound initialization and snapshots, preserve zero-budget read-only behavior, and preserve the guard around in-flight callbacks. Exercise this with a deliberately stalled storage read in both SDKs. | M |
| Medium | **Fuzz smoke tests cover string inputs with an empty execution context.** The template target always constructs a JSON string. Nested values and output-dependent substitutions sit outside these inputs. CI runs both existing targets for 60 seconds each. [Expression target](../../fuzz/fuzz_targets/expression.rs#L5) · [Template target](../../fuzz/fuzz_targets/template.rs#L5) · [CI budget](../../.github/workflows/ci.yml#L494) | Extend template inputs to bounded objects and arrays with populated context and outputs. Seed sequence validation and frozen-bundle decoding with accepted and rejected inputs. Keep short CI runs and measure coverage before increasing the scheduled budget. | M |
| Medium | **SQLite patch verification stops at dependency resolution.** The vendored manifest raises the SQLite dependency floor and every checked lockfile resolves `libsqlite3-sys 0.39.1`. CI checks the lockfiles for advisories. Those checks establish the dependency version, while a release-artifact test would establish the SQLite version actually loaded, including externally linked profiles if shipped. [Patch rationale](../../vendor/sqlx-sqlite/PATCH.md) · [Driver features](../../vendor/sqlx-sqlite/src/lib.rs) · [CI advisory checks](../../.github/workflows/ci.yml#L99) · [RustSec advisory](https://rustsec.org/advisories/RUSTSEC-2026-0459.html) | Query `sqlite_version()` on release artifacts for applicable server, native, and mobile builds and check against the fixed SQLite range for each linkage mode. Use the same gate to retire the patch once upstream resolution permits it. | S |

## Verification and performance

- The root workspace pass checked the host target with `cargo check --offline --locked --workspace --target aarch64-apple-darwin`. The `wasm32-unknown-unknown` target check, formatting check, and diff check also passed.
- The host WASM test run passed 227 tests. A small probe verified that the playground reports a completed dry run with a mocked child. The same sequence sent through the built CLI contract runner was rejected with the unsupported-child diagnostic.
- The extended pass resolved all four locked dependency graphs offline for `aarch64-apple-darwin`. A scan of each lockfile against the cached Rust advisory database found zero known vulnerabilities and one root-workspace maintenance advisory. Node and Python runtime checks, fuzz smoke runs, and SQLite linkage are separate from these metadata and advisory checks. This pass inspected the standalone sources and CI configuration. [RustSec maintenance advisory](https://rustsec.org/advisories/RUSTSEC-2026-0374.html)
- A host debug-build probe ran 50 flat, mocked `noop` sequences per size through JSON decode, interpretation, and JSON serialization. These figures describe local interpreter and response growth. Production worker throughput, PostgreSQL latency, and full-workspace line coverage were outside the measurements.

## Recommended sequence

1. Confirm the gRPC fairness and shutdown findings with deterministic regression cases and fix them independently.
2. Write one acceptance matrix for transport admission and worker rollout. Apply it to the shared policies before expanding version negotiation.
3. Define the native timeout contract and add shared release-artifact lifecycle tests for Node and Python. Add SQLite linkage checks to the artifact jobs. Extend the existing workspace lint lane to the standalone binding and fuzz manifests.
4. Publish a verification scope for preview and contract runs. Add child-workflow parity fixtures and structured fuzz inputs before moving runtime code.
5. Baseline query counts and CLI feature composition. Use the results to choose narrow storage dependencies and targeted batch work.

Re-review after the admission matrix is green across HTTP, gRPC, SQLite, and PostgreSQL. Re-run the shutdown fault test before the next server release.
